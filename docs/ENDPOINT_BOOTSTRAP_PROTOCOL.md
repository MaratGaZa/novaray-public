# Протокол выбора endpoint и DNS-bootstrap при kill switch

Статус: **предложение, документация задачи 70**, 2026-09-18. Владелец: MaratGaZa.
Основание: [ADR-003](./ADR-003-NETWORK-TOPOLOGY.md), [FR-008 RU](./SPEC_RU.md),
[FR-008 EN](./SPEC_EN.md), задачи 68–69 в [плане](./IMPLEMENTATION_PLAN.md).
Это каноническое описание предлагаемого lifecycle, не реализованный resolver или runtime.
ADR-003 остаётся `Proposed`; Gate H, DNS-leak и reconnect evidence отсутствуют.

## 1. Фактическая граница

[`KillSwitchAllowlist`](../src/kill_switch.rs) сопоставляет уже заданный IP/port/transport/uplink.
[`ConnectNetworkIntent::kill_switch_allowlist`](../src/network_transaction.rs) строит отдельную
policy; `plan()`/`execute()` её автоматически не потребляют. Эти API не разрешают имена,
не хранят DNS-снимок/срок действия, не наблюдают смену сети и не применяют firewall.
Описанные ниже состояния и переходы ещё не являются Rust API.

## 2. Инварианты предложения

1. Под активной, унаследованной или неопределённой защитой прямой DNS запрещён. Reconnect,
   ошибка резолвинга, истечение срока и смена сети не дают разрешения снять deny даже временно.
   Исключения для публичного, системного или встроенного в движок resolver не добавляются.
2. До первого protected connect разрешение имени возможно только в явно обозначенной
   незащищённой bootstrap-фазе: пользователь начал соединение, нет active/inherited deny,
   pending recovery и неизвестного системного состояния. Если продукту требуется always-on
   защита уже до bootstrap, этот вариант недопустим: остановка, а не скрытое послабление.
   UI обязан сообщить, что начальное разрешение имени идёт вне VPN; оно может раскрыть имя
   VPN-сервера. Это не evidence защиты DNS или остального трафика до активации kill switch.
3. В protected-фазе разрешён ровно один выбранный endpoint tuple. Список A/AAAA не превращается
   в список одновременных firewall-исключений; широкого разрешения IP без порта/transport нет.
4. Профильное имя сервера, TLS/SNI/Reality identity и выбранный сетевой IP различны по назначению.
   Выбор IP не меняет проверяемую identity, не отключает certificate verification и не доказывает
   подлинность сервера. Движок получает числовой адрес без собственного direct DNS fallback.
5. Все переходы сериализованы с connect/recovery. Обработчик проверяет контекст и актуальность
   непосредственно перед выдачей разрешения; поздний DNS-ответ старого запроса не меняет policy.
   Адреса, hostname, network/session IDs и ответы resolver не попадают в обычные логи.

## 3. Снимок кандидатов и закрепление адреса

Будущий resolver возвращает ограниченный результат: не более 16 уникальных IP-кандидатов для
одного профиля и запроса, с монотонным deadline пригодности каждого, поколением профиля/запроса
и наблюдаемым network context. Это проектный предел, не утверждение о системном DNS API.
Пустой, превышающий лимит, недостоверно датированный или несогласованный результат отвергается;
нельзя молча усечь ответ или получить бессрочное разрешение из cache без срока. Размер исходного
ответа и цепочка alias также должны ограничиваться адаптером до построения списка.

Кандидат проходит ограничения endpoint из задачи 69 и проверку поддерживаемого uplink address
family. Повторы удаляются, неподдерживаемые/невалидные адреса не получают разрешений; если
пригодных нет, соединение не начинается. Для воспроизводимости применяются фиксированный порядок
семей IPv4 → IPv6 и сортировка адресов внутри семьи; параллельных Happy Eyeballs-разрешений нет.
Это консервативный первоначальный выбор; изменение порядка или параллелизма требует review.
Порт и transport берутся из валидированного профиля, не из DNS-ответа.

Network context должен учитывать проверенный экземпляр uplink, поколение наблюдения и изменения
сети/маршрутов/resolver, а не только строку `en0`. Потеря наблюдения, неопределённость после wake,
reboot или пропуск событий делают снимок непригодным. Имя интерфейса не доказывает его идентичность.
Для IP literal DNS-снимок не нужен, но все ограничения адреса, контекста, сессии и policy действуют.

Выбранные IP/port/transport, профильная identity и network context закрепляются за одной сессией.
Истечение DNS deadline не переключает уже установленный, проверенный канал само по себе; оно
запрещает **новую** попытку по этому кандидату. Успешное соединение не продлевает DNS deadline.
Reconnect означает новую попытку, даже если tuple тот же. Смена профиля или network context
инвалидирует все кандидаты и закрепление; их нельзя переносить по совпадению имени интерфейса.

## 4. Переходы и отказ

| Состояние / событие | Допустимое действие | Обязательный отказ |
|---|---|---|
| Первый connect, достоверно нет защиты и recovery | Явный bootstrap, проверить снимок, выбрать один tuple, подготовить snapshot/journal и deny до redirect/DNS | Ошибка/пустой ответ: не запускать engine и не показывать Connected |
| Active/inherited deny, unknown state или pending recovery при старте | Локальная диагностика/recovery; новые попытки не допускаются | Не запускать bootstrap resolver и не снимать защиту автоматически |
| Потеря канала в прежнем подтверждённом контексте | Под сохранённым deny возможна ограниченная повторная попытка ещё действительного кандидата | Не обновлять DNS напрямую, не продлевать deadline, не менять identity |
| Следующий A/AAAA-кандидат | Последовательно переключить на ещё действительный кандидат того же снимка по процедуре ниже | Не разрешать одновременно весь ответ и не расширять порт/transport |
| Все кандидаты истекли/исчерпаны, изменился адрес сервера | Blocked: сохранить deny, показать стабильную причину и локальное восстановление | Не получать новый ответ по uplink и не выполнять бесконечный retry |
| Смена сети, uplink, профиля; сомнение после wake | Инвалидировать снимок и старые исключения; Blocked | Не переносить старый tuple в новый контекст и не начинать direct DNS |
| Crash/reboot/потеря наблюдения | Recovery до нового connect; старый снимок не является разрешением | Не считать persisted cache, имя интерфейса или журнал доказательством свежести |

Retry budget и таймаут каждой попытки должны быть конечными и проверенными до реализации runtime;
повторы не продлевают снимок. Конкретные значения и наблюдение контекста требуют отдельного
implementation evidence. Разрешение DNS через уже проверенный туннель также не вводится этой фазой.

### Замена одного tuple другим

Под lifecycle lock и сохранённым deny: остановить старую попытку и её транспорт; записать intent;
отозвать старое endpoint-исключение и связанные established-state разрешения; подтвердить отзыв;
затем установить маршрут-исключение и разрешение нового tuple, проверить их и начать новую попытку.
Endpoint exclusion route не должен попасть в сам туннель. Повторно проверить context/deadline
перед новым разрешением. На любом промежуточном сбое не выдавать следующее разрешение.

Ни отсутствие старого правила в плане, ни завершение engine не доказывают очистку состояния ОС.
При неизвестном результате — диагностируемый Blocked/recovery, без автоматического продолжения.
Компенсация не возвращает устаревший tuple и не снимает защиту ради успешного retry. Доступность
может быть потеряна; если native adapter не доказывает такую замену, переключение не поддерживается.
Существующий reverse rollback executor пока этого различия не реализует; старые журналы здесь
не переписываются и не объявляются доказательством безопасного reconnect.

### Явное завершение защиты

Blocked предлагает локальное действие без доступа к сети. Новый незащищённый bootstrap возможен
только после отдельного подтверждения пользователем прекращения защиты и проверенного полного
восстановления исходного состояния. Это осознанный disconnect, не reconnect и не DNS-fallback.
При ошибке rollback состояние остаётся recovery/unknown; успех и доступность сети не обещаются.
Crash, timeout, SIGTERM или закрытие UI не заменяют это подтверждение. Существующие требования
очистки/rollback сохраняются, но не разрешают незаявленный direct fallback при активной защите.

## 5. Альтернативы и пересмотр

- Разрешить resolver как третье uplink-исключение: отложено; нужен отдельный scoped контракт,
  аутентификация/привязка resolver traffic и packet-level evidence. Не штатный fallback.
- Разрешить все A/AAAA одновременно: отвергнуто для первоначального варианта; расширяет policy
  и усложняет отзыв старых разрешений. Сейчас цена узкой policy — последовательные попытки.
- Автоматически выключать kill switch ради нового DNS: недопустимо при активной защите.
- Refresh через проверенный туннель: отдельная будущая задача, не подразумеваемая возможность.

Цена предложения — отсутствие прозрачного reconnect после смены сети или исчерпания снимка.
До production необходимы review владельца, future pure-state tests и Gate H по
[матрице TESTING](./TESTING.md#endpoint-bootstrap-и-reconnect-задача-70).
Пересмотреть при добавлении multi-endpoint/always-on/runtime resolver или native firewall adapter.
Apple API, signing, entitlements, privileges и distribution не меняются; новых внешних фактов
эта ревизия не вводит. Откат документации не требует миграции или изменения ОС.
