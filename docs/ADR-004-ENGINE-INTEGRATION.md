# ADR-004: Интеграция протокольного движка VLESS/Reality

- Статус: Proposed
- Дата: 2026-08-16
- Ревизия: 2026-08-17 — движок пересмотрен в пользу sing-box после проверки поддержки per-app routing
- Решение требуется до: реализации раздельного туннелирования по приложениям (M3) и выбора production engine

## Контекст

NovaRay использует протоколы VLESS, TLS и Reality (XTLS) для защищённого туннелирования трафика. Реализация собственного криптографического стека Reality с нуля на Rust является избыточно сложной и несёт высокие риски совместимости. В индустрии стандартом де-факто для протоколов семейства VLESS/Reality являются два проверенных open-source движка: **Xray-core** (проект XTLS) и **sing-box** (проект SagerNet).

Владелец продукта зафиксировал 2026-08-17, что **раздельное туннелирование, включая правила по приложениям, является главной функцией продукта наравне с самим VPN**, а целевые платформы — macOS, Windows и Android. Это переводит per-app routing из желаемой возможности в требование выбора движка.

Для интеграции движка в NovaRay необходимо решить следующие вопросы:
1. Выбор протокольного движка (Xray-core vs sing-box).
2. Способ размещения движка в системе (изолированный дочерний процесс Subprocess vs встроенная библиотека Embedded C/Go Framework).
3. Управление жизненным циклом (Supervision): запуск, валидация конфигурации, мониторинг готовности (readiness), логирование без утечки секретов и корректное завершение (graceful stop).
4. Лицензионная чистота и правила распространения.

## Проверенные факты

Факты ниже проверены 2026-08-17 по исходникам и документации зафиксированных upstream-релизов.

1. **Xray-core `v26.3.27` не поддерживает маршрутизацию по приложениям.** В `infra/conf/router.go` структура правил не содержит полей сопоставления с процессом; поиск `process_name`, `process_path`, `package_name` по файлу даёт 0 совпадений. Правила ограничены доменом, IP, портом, протоколом, source и inbound tag.
2. **sing-box `v1.13.18` поддерживает маршрутизацию по приложениям на всех целевых платформах.** `docs/configuration/route/rule.md` объявляет `process_name`, `process_path` и `process_path_regex` с пометкой «Only supported on Linux, Windows, and macOS», а `package_name` — для Android.
3. sing-box содержит встроенные TUN, DNS и routing подсистемы; Xray-core требует внешнего tun2socks для получения системного туннеля.
4. Оба движка предоставляют CLI-валидацию конфигурации: `xray run -test -c` и `sing-box check -c`.
5. Лицензия sing-box — GPL-3.0-or-later с дополнительным ограничением по имени/ассоциации SagerNet; лицензия Xray-core — MPL-2.0.

## Рассмотренные варианты

| Критерий | Xray-core (`v26.3.27`) | sing-box (`v1.13.18`) |
|---|---|---|
| **Раздельное туннелирование по приложениям** | **Отсутствует** (факт 1) | **macOS/Windows: `process_name`, `process_path`; Android: `package_name`** (факт 2) |
| **Системный туннель (TUN)** | Требует внешний tun2socks | Встроенный TUN |
| **DNS и routing** | Требуют отдельной сборки policy | Встроенные подсистемы |
| **Лицензия upstream** | Mozilla Public License 2.0 (MPL 2.0) | GNU General Public License v3.0 or later (GPL-3.0-or-later) with SagerNet name/trademark exception |
| **Поддержка VLESS + Reality** | Эталонная (родина протокола XTLS Reality) | Полная (собственная реализация на Go) |
| **Валидация конфигурации** | `xray run -test -c <config.json>` | `sing-box check -c <config.json>` |
| **Embedded режим** | `libXray` (gomobile/cgo `xcframework`) | `experimental/libbox` (Apple и Android) |
| **Текущий статус в NovaRay** | Реализован генератор `xray_generator.rs`, проверен реальным бинарником | Манифест зафиксирован в спайке Issue #12 |

## Предлагаемое решение

1. **Архитектурная модель интеграции:**
   - NovaRay Core (`novaray-core`) сохраняет роль единого центра управления, абстрагированного от конкретного бинарного движка.
   - Core отвечает за: парсинг VLESS URI, генерацию валидного JSON-конфига, управление профилями и правилами раздельного туннелирования (routing rules), валидацию перед стартом и супервизирование процесса.

2. **Production-движок — sing-box (`v1.13.18`).**
   - Основание — факты 1–3: главная функция продукта (per-app split tunneling) технически недостижима на Xray-core ни на одной из трёх целевых платформ, а на sing-box поддержана нативно на всех трёх.
   - Существующий список `SplitTunnelingSettings::direct_apps` отображается в правила `process_name`/`process_path` (десктоп) и `package_name` (Android). При переносе требуется нормализация: sing-box сопоставляет имя и путь исполняемого файла, а не bundle identifier.
   - Встроенные TUN/DNS/routing снимают необходимость отдельного tun2socks-слоя, что напрямую влияет на объём работ по ADR-003.

3. **Xray-core сохраняется как проверенный совместимый путь, но не как цель.**
   - Реализованный `src/xray_generator.rs` и пройденный E2E остаются валидным evidence и используются как эталон корректности пайплайна `config → engine`.
   - Xray-core остаётся допустимым дополнительным движком для сценариев без per-app правил; удаление кода из репозитория этим ADR не предписывается.
   - Переключение выполняется через engine-neutral контракт Core, а не заменой генератора «на месте»: генератор конфигурации становится сменяемой стратегией.

4. **Модель управления процессом (Supervisor Target Contract):**
   - Управление процессом движка реализуется в модуле супервизора Rust Core (`ProcessSupervisor`):
     - **Pre-flight проверка:** обязательная валидация конфигурации CLI-командой движка (`sing-box check -c`, для Xray-core — `xray run -test -c`) перед попыткой запуска.
     - **Изоляция:** запуск процесса без повышенных привилегий (не от `root`).
     - **Потоки вывода:** перехват stdout/stderr через ограниченные по размеру буферы (bounded circular buffer) с автоматической очисткой персональных данных и IP/UUID (redaction).
     - **Graceful Stop & Residue Control:** остановка через сигнал `SIGTERM` с контролируемым таймаутом; при превышении таймаута — принудительный `SIGKILL`. Процесс не должен оставлять зомби-процессов или открытых сокетов.

5. **Гейты, требуемые до перевода ADR в `Accepted`:**
   1. *Config Generation:* генератор sing-box-конфигурации проходит `sing-box check -c` на реальном бинарнике.
   2. *Config Rejection:* доказанный отказ от запуска при невалидной конфигурации.
   3. *Readiness Probe:* локальная проверка готовности порта с таймаутом до переключения трафика.
   4. *Bounded Logs:* логирование без утечки ключей и UUID.
   5. *Graceful Stop:* остановка по сигналу за отведенное время.
   6. *Zero Residue:* отсутствие процессов-сирот после аварийного завершения.
   7. *Per-App Routing:* правило `process_name` доказанно направляет трафик конкретного приложения в отдельный outbound на реальном трафике.
   8. *Packet Flow:* корректный обмен пакетами с виртуальным интерфейсом (см. ADR-003).
9. *Legal Review:* формальное подтверждение условий GPL-3.0-or-later и naming restriction для выбранной модели распространения (см. ADR-002).

### Engineering legal review для public source snapshot (2026-08-18)

Для публикации исходного snapshot выбран `GPL-3.0-or-later`; полный текст лицензии находится в
[`LICENSE`](../LICENSE), а attribution и отдельное naming/association restriction upstream — в
[`NOTICE`](../NOTICE). Snapshot не содержит и не распространяет бинарник sing-box, не использует
названия sing-box/SagerNet как название продукта и явно отказывается от заявления об аффилированности.

Это закрывает engineering-часть gate 9 только для публикации текущего source-only snapshot. Gate 9
открывается повторно перед vendoring, embedding или распространением sing-box, а также перед выбором
конкретного macOS/Windows/Android distribution package. Это не юридическая консультация и не меняет
статус ADR `Proposed` до выполнения остальных gates 1–8.

## Последствия решения

### Положительные:
- Главная функция продукта — раздельное туннелирование по приложениям — становится технически достижимой на всех трёх целевых платформах.
- Встроенные TUN, DNS и routing снимают потребность в отдельном tun2socks-слое и уменьшают объём собственного привилегированного кода.
- Единый движок на macOS, Windows и Android означает единый формат конфигурации и один генератор в Core вместо трёх.
- Возможность валидировать конфигурацию до запуска сетевого туннеля, исключая падения в runtime.
- Изоляция сетевого движка в отдельном процессе защищает UI и Core от сбоев внутри Go-рантайма.

### Отрицательные / Риски:
- GPL-3.0-or-later предъявляет более строгие требования к распространению, чем MPL-2.0 у Xray-core; для выбранной модели дистрибуции требуется отдельный legal review (гейт 9).
- Реализованный и протестированный генератор Xray-конфигураций перестаёт быть основным путём; часть работ M1/M2 не переиспользуется напрямую.
- Naming/association restriction SagerNet ограничивает подачу продукта как связанного с sing-box.
- Размер дистрибутива увеличивается за счёт включения скомпилированного бинарного артефакта движка.
- Необходимость управления межпроцессным взаимодействием и контролем жизненного цикла дочернего процесса.

## Условия пересмотра

- Появление per-app routing в Xray-core делает сравнение открытым заново.
- Отрицательный legal review по GPL-3.0-or-later для выбранной модели распространения возвращает вопрос к Xray-core с отказом от per-app правил либо к собственной реализации сопоставления процессов над локальным прокси.
